# The game in more than one language

English and French ship today. The framework is `src/game/i18n.ts` (about 150
lines, no dependency), the dictionaries are `src/locales/*.json`, and two probes
stop the usual silent failures reaching a phone.

## Adding a string

1. Put the English in `src/locales/en.json`, under the namespace it belongs to.
   `en.json` is the source of truth: every other file answers to it.
2. Put the translation in every other file in that directory, at the same key.
3. Call it: `t('menu.newCareer')`, or `t('menu.continue', { manager, club })`.

That is the whole workflow. `npx vite-node scripts/i18nprobe.ts` fails if a key
is used and missing, missing from a translation, or carries different
placeholders in one language than another.

### Placeholders are named, never numbered

```json
"continue": "▸ Continue - {manager}, {club}"
```

A numbered or positional placeholder locks the sentence to English word order,
which is the single most common way a game gets localised badly. Named ones let
a translator move the pieces:

```json
"savedAt": "{season}, semaine {week}"
```

Numbers passed through `t()` are formatted for the locale on the way in, so a
French screen reads `12 000` rather than `12,000` - which a French player would
otherwise read as a decimal point.

### Plurals

An entry shaped `{ "one": ..., "other": ... }` is a plural, filled from `vars.n`:

```json
"injured": { "one": "{n} blessé", "other": "{n} blessés" }
```

English splits at `n === 1`. French keeps the singular for 0 as well, which
`t()` already knows; a language with more forms than two needs a rule added to
`t()` rather than a new key.

## Adding a language

1. Copy `en.json` to `src/locales/<code>.json` and translate the values.
2. Add the code to `Lang` and to `LANGS` in `src/game/i18n.ts`. The label goes in
   the language itself - "Français", not "French" - because somebody hunting for
   their language is scanning for the word they would use for it.
3. Add its number locale to `fill()` and its plural rule to `t()` if it needs
   one.
4. Run `scripts/i18nprobe.ts`. It will list every key you have not translated.
5. Run `node scripts/langprobe.mjs` after a build. It measures the bottom nav and
   the submenu at 412px, which is where a longer language shows up as a layout
   bug rather than a translation one.

## Where the choice lives

On the title screen, directly under the text size control, because it has to be
answerable before a career exists: a French speaker should not have to start one
in English to find the switch. Stored in `localStorage['rm-lang']`; with nothing
stored, the device's own language decides, but only between languages the game
actually has.

`store.lang` mirrors `i18n.getLang()` and `App` subscribes to it. That mirror is
load-bearing: `t()` is a plain function call, so without a store field nothing
would re-render when the dictionary under it changed, and the title screen would
stay English until something else happened to repaint it.

## What is translated so far

The chrome and the front door: the title screen, the new-career wizard, the
bottom nav, the three submenus and every screen title. That is the whole of a
player's first minute, plus the frame around every screen after it.

Not yet: the screens' own bodies, and the match engine's prose. The engine alone
is about 68,000 words of generated commentary and reports, built from templates
that interpolate players, clubs and numbers - it is a translation project rather
than an extraction, and it wants doing in one pass with a translator who can see
the sentences, not in pieces.

## The English side is a test selector

Forty browser harnesses find controls by their visible text - `text=New Career`,
`.submenu-item >> text=Tactics`. Rewording the English half of the dictionary
therefore reworks those tests, silently, into timeouts with no clue attached.
`i18nprobe` pins the handful they lean on hardest; the rest is a thing to keep in
mind before tidying English prose that reads fine.
